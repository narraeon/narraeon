# 已发布持久格式必须提供原子迁移

正式发布或公开预发布过的 Narraeon 持久格式建立了升级兼容义务，不能因为新格式更干净就拒绝旧世界。对于能够精确识别的已发布 schema，Runtime 在首次使用前执行一次性、幂等迁移：保留旧源，先写完并验证当前不可变事实和投影，最后发布当前 Authority 小端点作为整个新布局的 durable marker；任一切点退出都从旧源和已写事实继续，不重放 Provider 或 Authority。

迁移完成后 Runtime 只读写当前格式，旧累计文件不再增长。迁移链只保证从上一个主要存储格式升级，更早的格式需经过中间版本：例如 v0.2.0 及更早创建的世界须先由 v0.3.0–v0.6.0 打开一次，之后才能由当前版本迁移；早于 Authority V3 的格式不再由当前 Runtime 迁移，遇到时以不可打开处理且不改写世界数据。我们拒绝长期双读／双写和对未知格式的启发式兼容，因为它们会把旧复杂度永久泄漏到正常读写 seam，并让损坏数据与真实旧版本无法区分。

后置编排的 `narraeon.play-call-chain/v1` 保持原解析以恢复历史绑定；当前编排方案直接使用 `narraeon.play-call-chain/v2` 的有序 `followupItems` 引用。用户正文、资源、产物与显示配置仍在同一文件树，停用不删除；已升级的编排方案保留只读项。系统和内容包占位身份使用含冒号的保留作用域，避免与已发布的用户 ASCII 身份碰撞。

兼容样本必须由对应历史实现写出并标注确切来源，不能把当前对象删改字段后当作已发布存档。v0.4.0 及此前的作者创作会话只保存在进程内，没有可跨重启迁移的作者会话文件；后来引入的旧持久作者 schema 另按明确版本兼容，不把它冒称为这些发布版的持久格式。编排方案、世界、已保存请求与产物分别保留自己的历史编码及资源；新编排只影响后续主动发送。

编排方案库从 `file-native-play-presets.json` 一次性迁移至 `file-native-orchestrations.json`。新库的原子发布是迁移完成标记。当前和可解析草稿使用 `orchestration.yaml` 与 `narraeon.orchestration/v1`。历史修订、不可解析草稿和旧源保留原字节。旧 v1 的可编辑正文成为用户条目，对应系统政策停用以避免重复。旧 v2 按发布时的必选身份校验后转为叠加，旧 v3 沿用叠加内容。新建默认与应用模板直接使用当前格式，目录演进通过有效编排解析，冻结请求和运行资源沿用自己的快照和 codec。

v1.0.0 保留 pre-1.0.0 已支持的历史迁移、旧编排便携导入和旧书签。后续清理见 [#244](https://github.com/narraeon/narraeon/issues/244)，该工单同时核查已升级世界中仍合法存留的冻结历史。
