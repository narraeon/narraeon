# 跑团玩法是世界身份，判定由 Runtime 从世界派生

玩法模式是内容包与世界的身份属性。内容包创建时在互动式小说与跑团之间二选一，选择保存在 `control/gameplay.json`（`narraeon.gameplay/v1`）中；缺失该文件即为互动式小说，因此既有内容包无需迁移。跑团包另带判定方案 `d20`、`d100` 或基础混乱袋，方案可在内容包创作中改写，模式永不改变。世界创建时复制内容包的玩法并固定，世界修订与控制编辑都不能修改它；之后对内容包的编辑只影响之后新建的世界。复制、导入、导出与分叉都继承玩法。

判定的机械规则不由预设承载，而由 Runtime 从世界玩法派生。工作区仍只有一份当前玩法预设，服务所有模式与方案。每次正常发送时，跑团世界获得该方案的判定工具及 `roll_dice`、`calculate`，互动式小说不获得任何判定工具；世界占位处的只读跑团规则块同样由 Runtime 生成。跑团指导是仅在跑团编译中展开的内置提示 `play.tabletop` 与 `author.tabletop`，互动式小说请求保持逐字节不变。既有预设通过一次性原子迁移补入这两项（[ADR-0034](0034-released-storage-formats-require-atomic-migrations.md)）。

判定中 Runtime 拥有随机、算术、比较、工具契约与持久结果，AI 拥有行动目标、字段、数值、难度、世界规则、叙事与世界更新。成功必须兑现声明的目标，失败不得兑现它；关键结果来自固定机械规则，不能在抽样后由 AI 改写。每次游玩推进保存一个秘密随机种子，同一执行恢复时不重新抽样，新时间线可以重新掷骰。判定回执随 `tool_result` 时间线事件保存，模型收到本地化文本，界面从结构化字段渲染卡片。无效参数只是工具错误，不构成角色行动失败。

这样划分的理由有三点。第一，玩法是世界的事实，预设是跨世界复用的作者框架；把判定绑进预设会让同一份用户预设随方案分裂，并让用户定制过的预设对跑团世界失效。第二，派生让方案改动只改变下一次发送的工具与规则块，不改写任何预设，读取路径也无需创建或写入预设。第三，机械保证留在 Runtime，语义判断留给 AI，与 [ADR-0029](0029-author-prompt-layers-split-by-capability.md) 的能力划分一致，也让随机与持久结果可以独立验证（[ADR-0001](0001-runtime-is-the-sole-committer.md)）。

被拒绝的方案：

- **按判定方案绑定预设**。做法是每种方案一份预设副本，或工作区按方案记录当前预设选择。它把用户定制分散到多份副本，使跑团世界丢失已经定制好的预设，并需要读取路径自动补建预设。
- **只允许手动编辑 JSON 修改方案**。方案是有限且可校验的配置，应有结构化入口。仅靠原始文件编辑时，无效值只能在保存时才被发现，界面也无法说明当前方案；AI 改写方案时同样需要回执明确告知新规则。
- **允许在两种模式之间切换**。互动式小说与跑团的状态、历史和工具全集没有可迁移的含义，已有世界的历史与工具契约无法保持。
