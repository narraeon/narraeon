# 世界状态维护与上下文衔接

写入回执、预览、设定完善检查共用真实材料编译器。成功写入后的回执说明“按当前状态和配置，若现在开启全新上下文”的正文、节点和目录摘要覆盖；它不会声称冻结上下文已重新注入。覆盖判定失败会说明原因，并保留真实写入结果。

## 主持怎样维护连续性

默认玩法预设使用三档保存规则：玩家视图显示的值发生变化时，本轮最终叙事前写回；需要保存但玩家原文与最终叙事没有记录的信息当场保存；其余可恢复状态在事件收尾集中归并。时间推进由主持根据行动、等待、赶路、休息等情境判断。Runtime 标记玩家视图的真实文档与节点绑定，不推断时间增量或赋予额外读取权限。

主持整理自然所有者、重要认知、承诺和有界文档后，可调用空参数 `world_checkpoint {}`。工具先确认登记，最终叙事成功提交后检查点生效。叙事下方显示开启全新上下文的建议；点击只准备下一次输入，玩家仍需主动提交。

新上下文完整补入最近可达检查点之后的玩家原文与最终叙事；没有检查点时从世界起点开始，开场白不重复注入。尾段非空会替代 recent 历史选择，即使 frame 没有 history slot 也补入；尾段为空仍采用 recent 声明。补充不包含思维链、工具调用、工具结果或工具中间文本，不设 Runtime 重放预算。每条真实玩家输入前另附完成回合数；空输入续写不增加回合，历史范围按精确消息位置选取。

默认保存规则属于新默认预设和可编辑作者提示。已有用户编辑、复制或导入的预设保留原文，既有模型上下文继续采用冻结的提示与工具集合。

## 可选的整理提示

在世界控制编辑器中，可为文档和材料槽填写建议体积，也可选择记录写入时世界时间的明确节点。对应控制如下：

```yaml
maintenance:
  documents:
    '@current-situation': 8000
    '@alex': 12000
  clock:
    document: '@current-situation'
    locator: { yaml: [时间] }
context:
  - slot: { kind: document, document: '@world-rules', id: rules, advisoryBytes: 24000 }
  - slot: { kind: current_situation, id: scene, advisoryBytes: 10000 }
  - slot: { kind: additional_materials }
```

这是可合并到现有 frame 的局部示例，保留原来的 format、bindings 和 instructions。文档通过稳定短引用定位；材料槽 id 必须唯一、稳定，调序后保留。建议值为正整数 UTF-8 字节，不是 token，也不是写入或历史补充的硬限制。超限时工具回执仅附简短提示，完整报告在 Prompt Preview、设定检查和“AI 读取”中展示。

报告区分正文原始字节、去重后的实际注入贡献、世界材料总量、其中的检查点历史、作者与 Runtime 提示以及逻辑工具 JSON。单文档贡献包含其真实选取的标题和标记，合计不包含所有跨文档公共标记；不能把所有正文之和当作请求大小。

增长基准来自世界起点文档正文；游玩中新建文档使用第一次接受的正文，标为创建后新增。分叉保留来源基准，空基准不计算倍数。相对基准增长不代表冗余。

精确读取在正文外附最近已提交的正文和元信息变更位置。只有摘要变化时，正文位置保持不变；no-op、重启和文件复制不刷新位置。时间只记录明确绑定节点当次写入时的标量或 Markdown 文本；未绑定、节点不可读、复杂 YAML 对象或旧提交没有记录时显示未记录。此信息不代表角色知情程度。

## 诊断缓存顺序

“AI 读取”比较同一时间线上相邻新上下文的冻结编译结果，并另列当前世界的新上下文预测。报告给出逻辑文本公共前缀、变化来源及其顺序；文档表区分发生真实正文和元信息变化的上下文数，同一上下文多次修改只计一次。旧提交没有可识别上下文时，不伪造变更次数。

生产 Provider 首次派发时记录不含凭据的实际编码，用于核对 JSON 前缀、内容块、缓存断点和缓存键。没有历史记录的上下文显示缺少对照。JSON 公共字节和逻辑文本公共字节不等于 Provider 能命中的 token 前缀。CLIProxyAPI 的上下文隔离键保持原有语义；任何排序建议均需作者在控制中显式修改，并仅作用于新上下文。

报告保留 Provider 实际返回的 cache read、cache write 和 uncached input；缺失值显示未报告。相邻请求 usage 并非受控收益实验，不能据此宣称节省比例。真实模型的时间更新、检查点收尾、跨上下文连续性和缓存收益验收见 [Issue #29](https://github.com/narraeon/narraeon/issues/29)。
