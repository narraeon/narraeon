# 长存档打开与历史翻页基准

在仓库根目录，用项目要求的 Node 版本运行。只使用临时合成数据和本地脚本化模型，退出时清理存档。

```sh
npm ci
mkdir -p .scratch/324-world-open
node scripts/world-open-benchmark/measure.mjs > .scratch/324-world-open/results.json
node scripts/world-open-benchmark/measure.mjs --turns 500 --workload narrative --repeats 3
```

默认测试 500 和 2,000 玩家回合，每档分别跑正文主导与每轮写状态两种负载。每组做 5 次独立测量，JSON 保留原始样本、中位数、最小值、最大值和读盘计数。进度写到标准错误。可反复传入 `--turns` 和 `--workload` 选档。每次测量子进程默认最多 30 秒，由 `--timeout-ms` 调整。生成并验证每档存档的上限默认 90 秒，由 `--fixture-timeout-ms` 调整。超时保留在 JSON 里，超时样本不进入时间统计；打开或统计组子进程超时，当次相应整组都记为超时。

## 保存档及核验

- 一回合含一条约 90 B 的玩家原文和一条约 1 KB 的主持正文。正文主导每回合提交两次。状态负载额外执行一次 `world_patch`，改同一份 YAML 的数字字段 `watch`，形成第三次独立的 Authority 提交和三条额外的页面事件。两种档案正文完全相同，使用一个游玩上下文和 12 份状态文档，玩家视图读取 `watch`。
- 第一回合通过真实 `PlayCallChain` 和脚本化模型生成。其余回合用 Authority 的生产提交接口生成轮账本及当前文件，用游玩时间线存储接口生成标准事件、摘要、对话和工具回执。没有为后续每轮调用模型或保存请求诊断，也没有生成扩展产物。内容和提交数量可重现，文件时间戳随运行变化。
- 每档使用生产读取校验当前端点、主持原文、历史版本位置的 `watch`、完整持久时间线和两页无重叠的摘要。每次计时再次检查首屏和翻页结果，并用统计结果核验最后一次正文写入位置。案例采用当前存储格式，保留正常生成的持久摘要和与端点一致的首页活动缓存。

## 计时范围

| 路径 | 计时边界 |
| --- | --- |
| Runtime 初始化 | 新进程动态导入后，从构造 `V1Runtime` 到 `initialize()` 返回。独立于首次打开计时。 |
| 冷打开 | 该进程第一次 `V1Runtime.handle({ type: "world.read" })`。包括首次打开的存储校验与恢复检查、端点和玩家视图、最新 40 项摘要、修订及扩展状态等 Runtime 工作。 |
| 热打开 | 同一个 Runtime 紧接着读同一端点，保留进程内存储、账本和历史版本缓存。 |
| 较早一页 | 使用热打开返回的游标做一次 `play.timeline.page`，读上一页 40 项摘要。 |
| 重建维护统计 | 独立进程里先打开世界，计时调用 `FileNativeWorldStore.readDocumentMaintenance`。此时账本已在内存，维护统计缓存为空。另记录同实例、同端点立即再读的缓存命中。 |

计时走生产 Runtime 命令或存储读接口，范围止于方法返回。浏览器渲染、HTTP 封包、网络、进程和模块加载、后续玩法产物读取、全新上下文的其他编译工作均不在范围内。系统文件缓存保持自然状态，建档和校验已读过这些文件。冷打开指 Runtime 进程冷，数字不能代表冷磁盘。每次测量在 Node 的 `fs.promises.readFile` 上记录世界目录内的尝试与指定路径成功数，计数包含少量探针开销。它不统计 OS 物理读盘、目录枚举或内存扫描。

世界状态正文与元数据合计 2,656–2,659 B。建档加校验耗时 2.25、4.75、9.50、19.81 秒。维护统计命中内存缓存的中位数为 0.11–0.17 ms。

- **冷打开**每次成功读取全部账本记录，热打开无需再读这些记录。同样两个打开路径各读取 40 条摘要。代码中，玩家视图还通过 `recoverEndpoint` 构建全部已提交原文，随后只使用其中的状态文档。如果后续需要改善首屏延迟，可单独验证只读端点状态和控制是否能省下这份工作。首次恢复如何避免全盘检查需要单独评估恢复边界。
- **较早一页**四档均读取 40 条摘要、零条账本记录、零次账本头，总计 45 次文件读取尝试。暂不优化翻页。样本只覆盖一个长上下文中的上一页，跨多个上下文、更多文档及有产物的世界需要单独核验。
- **优先分析维护统计重建**。2,000 轮写状态时重建约 2.31 秒，已热账本没有重读轮记录，却读取账本头 10,002 次。源码逐轮获取提交，并为每次状态更新读取该端点的历史文件、打开文档快照。可以先验证在一份固定的账本视图中批量取得维护所需事实和版本，再区分重复端点读取、历史前像遍历和文档解析各自的成本。这条路径发生在全新上下文准备工作中，计时结果与首屏独立。
